# Migration and rollback plan (before production changes)

1. Preserve source/git/unrelated work; checksum source archives. Done locally; see audit.
2. Obtain authorized database access through secret environment, never browser dumps of medical/contact records. Capture schema, policies, roles, functions, tables, storage manifest and Auth identity mapping. Encrypt with an operator-owned age recipient. Verify decrypt, pg_restore listing and restore into isolated disposable Postgres; compare counts, foreign keys and logical checksums. Do not put production PII in staging.
3. Rehearse using synthetic fixtures. New normalized schema is additive in `club_app`; legacy tables remain untouched. Import every legacy ID through an explicit mapping. Quarantine unknown keys. Never translate email/PIN/localStorage into trusted identity. Invite/verify users and match membership only through admin review.
4. Stage new front end on a different origin and allowlist only an approved test project. Production URL is explicitly rejected. Verify email with provider sandbox; no real recipients without authorization. Require all quality gates, signed permit preview, member acceptance and strong admin auth.
5. At authorized cutover: maintenance read-only window; final encrypted backup + rehearsal evidence; revoke ALL old anon/authenticated table and function access (inventory deployed policies first); apply reviewed schema and data migration; validate counts and joins; enable Auth redirects, CSP and security headers on supported host; deploy only platform build output; smoke test independent member and admin accounts. Never deploy the repository root containing legacy code.
6. Observe error rate, RSVP conflicts, queue lag/failures and sign-in failures without PII. Reconcile totals and assignments. No automated publication is configured.

Rollback: keep writes paused; save post-cutover delta and outbox/provider IDs; redeploy previous *secure* release and apply forward repair. Do NOT restore insecure legacy anonymous grants. If DB restore is necessary, restore to a new isolated project, validate, reconcile post-backup RSVP/score events and delivered notification IDs, then switch configuration after authorization. Mark delivered jobs to avoid duplicate notices. Source rollback alone cannot undo schema/data changes. Target RPO: last verified daily backup (<=24 h before cutover; zero at maintenance snapshot). Target RTO: 2 h, provisional until a timed remote rehearsal succeeds.

Launch blockers: verified database backup and restore; actual deployed policy inventory; provider credentials/consent; production authorization; complete acceptance gates. Source archives do not satisfy these blockers.
